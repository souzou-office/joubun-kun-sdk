法令は毎週自動で更新している（`docs/law_update.md`）。一方、通達（`tsutatsu_chunks_v4`）と判例（`hanrei_v1`）は、PC で手で作り直したときの状態のまま止まっている。
これを法令と同じ考え方で毎週回す。

**オーナー決定（2026-09-24）**

- **GitHub Actions で回す**（法令の週次と同じ。PC を点けておかなくてよい）
- **今の版に上書きする**。書く前に、上書き・削除するファイルを退避する。版を分けて `wrangler deploy` で切り替えるやり方（v4 の作り方）は、年に 1 回程度の全件作り直しのときだけにする

質疑応答事例・裁決は、判例・通達の後に同じ形で足す。

## 共通の作り

- Worker は変えない。読むプレフィックス（`TSUTATSU_CHUNKS_PREFIX = tsutatsu_chunks_v4`、`hanrei_v1`）もそのまま。中身を差分で上書きする
- 流れは法令と同じにする
  - prepare: R2 に書かない。取得 → 差分 → 報告を作る
  - 安全チェック（blockers）に通り、見直す対象も無ければ、apply まで自動で流す
  - 止めたときは Issue でオーナーに知らせる。ラベルは `tsutatsu-update` / `hanrei-update`
  - 見直す対象がある回は、オーナーが Issue に「反映」とコメントしたときだけ流す
- apply
  - 上書き・削除する R2 のファイルを `update_state/{tsutatsu,hanrei}_backup/{run_id}/` に退避してから書く
  - ベクトルは、上書きする id と削除する id の両方について、今の値・metadata・namespace を退避してから upsert / delete する（`local_vec_v3.py backup` と同じ形）
  - 退避が 1 件でも失敗したら（R2 に書けない・Vectorize から読めない id がある等）、本番への書き込みを始めずに止めて Issue にする
- 埋め込みは Workers AI（`@cf/baai/bge-m3`）で作り、`AI_POOLING` は法令と同じ値にする
  - 通達の v4 はローカル GPU で作ったが、Workers AI との互換性は cosine 1.0000 だった
  - 毎回、法令の `check_embed_drift` と同じ自己一致検査を通す。0.98 未満なら止める
- 状態（台帳・既知の id・前回の写し）は R2 の `update_state/` に置く。Actions の cache や artifact には頼らない（消えると全件扱いになる）
- 取得の礼儀は今と同じ（1 秒 1 件・UA 明示・逐次）
- 条文ページのエッジキャッシュの鍵には配布バージョンとプレフィックスが入っている。ただ、上書きでは両方とも変わらないので、ページへの反映は最長 1 日遅れる（検索・MCP は R2 を直接読むのですぐ変わる）。これは許容する
- 費用: ¥0（取得・パース・R2・Workers AI の埋め込みは無料枠の範囲）。LLM を使うのは、通達の新しい紐付け（`13_assign`、1 本 ¥0.2 前後）だけ

## 段 1: 判例（`update_hanrei.yml`）

### 今のデータ（`scripts/hanrei/07_build_upload_r2.cjs`）

- `hanrei_v1/cases_{NNNN}.json`: id を 100 で割ったもの（4 桁）ごと。`{ id: record }`
- `hanrei_v1/lookup/caseno_{元号}{YY}.json`・`lookup/date_{YYYY}.json`: 事件番号と日付からの引き
- `hanrei_v1/links/{law_id}.json`: 条文 → 判例の逆引き。条キーごとに `{ total, items }`。items は裁判所の格の順 → 日付の新しい順で上位 300 件
- `hanrei_v1/index.json`: 件数など
- ベクトル: `tsutatsu-embeddings-v1` の namespace `_hanrei`（要旨 `{id}-y` とセクション `{id}-s{n}`）

### 毎週の流れ

```
prepare（R2 に書かない）
  a. 一覧を取る: 6 コレクション × 直近の 2 年（今年と去年。裁判年月日が古くても掲載が遅れて出るものを拾う）
     1 ページ 30 件。数百リクエスト（1 秒 1 件で 10 分前後）
  b. 新しい id = 一覧の id − 既知の id（R2 update_state/hanrei_state.json）
  c. 新しい id だけ、詳細と PDF を取る（01 の detail / pdf）→ 本文を抜く（02）→ パース（03）
  d. 審級の突合: 原審の引き当ては R2 の lookup（caseno / date）で行う（手元に全件を持たない）
     上級審が付いたら、原審の record の appeals に足す（原審のある cases ファイルも上書き対象）
  e. 埋め込み（06 と同じ文面・同じ metadata）
  f. 上書きするファイルの一覧を作る: cases（新しい id のもの＋appeals を足す原審のもの）・lookup・links・index

apply
  退避（R2 のファイルと上書きするベクトル）→ R2 上書き → Vectorize upsert → hanrei_state.json に既知の id を足す → 抜き取り検証
```

### 安全チェック（止める条件）

- 新しい判例が 1 週で 500 件を超える（一覧の読み取りが壊れて全部が新しく見えている疑い）
- 一覧の件数が読めないスライスがある。または、今年・去年のスライスの件数が前回より減った（取りこぼしの疑い）
- 新しい判例の本文が取れない・パースに失敗したものが 1 割を超える（1 割以下は飛ばして報告に出し、次の週にもう一度試す）
- 既存の record を上書きするとき、appeals 以外の欄が変わる（足すだけのはずなので、変わるなら何かがおかしい）
- 埋め込みの自己一致が 0.98 未満

### 実装（2026-09-25）

- コード: `scripts/hanrei/weekly/run.cjs`（`prepare` / `apply` / `restore <run_id>`）、ワークフロー: `.github/workflows/update_hanrei.yml`（日曜 07:00 JST。手動の `mode=prepare` / `restore` もある）
- **書く経路は 1 本**: apply・restore は Actions からしか動かない（run.cjs が手元での実行を拒む。確かめ用に R2 と Vectorize の両方を偽物にしたときと dry-run は別。片方だけ偽物は拒む）。書き込むジョブ（apply・restore）は concurrency（update-hanrei-write）で 1 本ずつ流れるので同時に書かない（ワークフロー全体には掛けない。関係ない Issue コメントが待機枠を奪わないように）。反映の道は「問題の無い回の自動反映」と「Issue への『反映』コメント」だけで、手動の apply は無い。見直す対象がある回（初回を含む）は、「反映」コメントの経路でなければ run.cjs も書かない
- 取得・本文・パースは既存の 01・02・03 をそのまま使う。作業フォルダは `HANREI_DATA_ROOT`（週次の state の下）で、PC の `hanrei_raw/`・`hanrei_parsed/`・`scripts/hanrei/state/` には触らない。ベクトルの文面と metadata は 06 の `caseToTargets`、並びと条キーの判定は 07 の関数を共用する
- **初回**: 既知の id の台帳（R2 `update_state/hanrei_state.json`）が無いので、R2 の `hanrei_v1/cases_*.json` の id から作る（読むだけ）。これを「見直す対象」にしているので、**最初の反映は必ずオーナーの「反映」コメントを通る**
- 安全チェック（止める）: 一覧ページが取れない・新しい判例が 500 件超・詳細が取れないものが 1 割超（3 件以上）・新しいはずの id が既に cases にある・原審の appeals 以外が変わる・埋め込みの自己一致が 0.98 未満か値が不正なものが 1 件でもある（既存の判例 5 件を埋め込み直して索引と比べる。比べられたのが 3 件未満なら、それとは別に見直す対象）・metadata の 10KiB 超
- 見直す対象（「反映」で流せる）: 初回・コレクション×年の件数が前回より減った（0 件に落ちたものも含む）・埋め込みのずれを 3 件未満しか確かめられなかった。件数の減少だけの回も、「反映」すると台帳の件数を新しくする（毎週同じ確認を出さない）
- 「反映」コメントは、引用（`>`）を除いた最初の行がちょうど「反映」のときだけ効く（「反映しないで」「反映は保留」では動かない）。この判定は書き込みの concurrency（`update-hanrei-write`）に入らない別のジョブ `approve` で行い、通ったときだけ apply を作る（何もしないコメントが、待っている restore を押し出さないように。GitHub の concurrency は待機を 1 つしか持たない）
- apply は成果物を厳しく読む（ファイルの欠け・JSON の壊れ・ベクトルの本数違い・id の重複・1024 次元でない・sid の食い違いがあれば書かない）
- apply は、prepare の後に R2 の対象ファイルが変わっていないこと（hash）を確かめてから、退避（ファイル・台帳・上書きするベクトル）→ R2 → Vectorize → 台帳 の順に書く。退避が 1 件でも失敗したら書き始めない
- 中間ファイル（NDJSON）に読めない行があれば、ファイル名と行番号を付けて止める（黙って飛ばさない）
- 詳細ページが取れなかった判例と、PDF が取れなかった・本文を抜けなかった判例は足さない（既知にしないので翌週もう一度試す）。裁判所が PDF を出していない（404）判例は本文なしで足す
- apply は prepare の後に台帳（`hanrei_state.json`）が変わっていないことも hash で確かめる
- 作業中の印は R2 の条件付き書き込み（S3 API の `If-None-Match: *`。`scripts/update/lib/r2.cjs` の `putIfAbsent`）で取る。Actions と手元の実行が同時でも取れるのは 1 つだけ。取った後にファイルと台帳の hash を照らし、外すのは自分の token のときだけ。書き始める前に止めたときは外す
- 印には段階（phase）がある。apply は 'backup'（退避中・本番はまだ）→ 'writing'（本番を書き始めた）。'backup' のまま残っていれば（退避の途中で強制終了など）本番は変わっていないので、mode=restore で印だけ外せる（退避が無くても）
- apply は書き始める前に反映中の印（R2 `update_state/hanrei_apply_inprogress.json`）を置き、台帳まで書き終えたら消す。restore も書き始める前に「戻し中」の印を置き、全部戻し終えたら消す。途中で落ちて印が残っていれば、次の prepare・apply は止まる（書きかけ・戻しかけを前提に進めない）。同じ回の restore はやり直せ、別の回の restore は印が残っている間は拒む
- 止めた回（blockers 付き）の成果物は途中までしか作らないので、強制反映（force）の道は作らない。原因を直して prepare からやり直す
- 戻す: Actions の `mode=restore`・`restore_run_id`（main のコードで動く）。各ファイルとベクトルが「その回の書いた後」か「書く前」（apply が途中で落ちた）のままのときだけ戻し、後に別の反映が入っていれば何も書かずに止まる（ベクトルは float32 で返るので metadata の一致と cosine 0.9999 以上で比べる）。戻す元（退避のファイル・ベクトル）は書き戻しの前に全部読み、書く前の hash や上書きした id と合わなければ何も書かずに止まる。戻す直前の中身（ファイル・ベクトル）も `pre_restore_*` に控える。消すのはその回に新しく足したベクトルだけで、上書きした既存のベクトルは退避の値で上書きする（途中で落ちても restore をやり直せば戻る）
- 確かめ: `HANREI_PYTHON=<pdfplumber と reportlab の入った python> node scripts/hanrei/weekly/check_weekly.cjs`（¥0。偽の裁判所・R2・Vectorize・埋め込み。54 項目）

### 週次で拾えないもの（年 1 回の全件作り直しで拾う）

- 一覧の窓（今年と去年）より前の裁判年月日で、後から掲載された判例
- 既存の判例の中身の差し替え（裁判所が詳細ページや PDF を直した場合）
- 既存の上告審が、後から掲載された原審を指している場合の引き当て（新しい判例 → 既存の原審、新しい判例どうし、は引き当てる）
